# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A web app (`index.html`, ~475KB, all HTML/CSS/JS inline) for staffing and commercial-pipeline management at Eagleprojects (rilievi/surveying department). Hosted on GitHub Pages, backed by Supabase (Postgres + Auth + Realtime + Edge Functions). No bundler, no package.json — `index.html` is still the deployed artifact, but it is now a **generated file**, not the source of truth (see "Source layout" below).

Live app: https://mmarchetti95.github.io/Gestione-Staffing/

## Source layout (since the `refactor/split-files` split)

`index.html` used to be hand-edited directly. It is now assembled by `scripts/build.py` from:
- `src/head.html` — everything from `<!DOCTYPE html>` up to and including the `<script>` opening tag (head, CSS, body markup, CDN `<script src>` tags).
- `src/js/*.js` — the app's JS, cut at the pre-existing `/* ===== ... ===== */` section banners, one file per section/group of sections. **Order matters**: `scripts/build.py` concatenates them in the exact order listed in its `JS_FILES` array, which reproduces the original top-to-bottom order of the single `<script>` block — this preserves the relative registration order of the two `DOMContentLoaded` listeners (dashboard init, then weekly-planning init).
- `src/tail.html` — `</script>` through `</html>`.

`supabase/functions/` is **not** part of the build — it holds Edge Function sources (Deno/TypeScript) that run server-side on Supabase and never reach `index.html`. `scripts/build.py` ignores it.

**Edit `src/js/*.js`, never `index.html` directly.** After editing, regenerate with:

```bash
python3 scripts/build.py
```

`scripts/smoke_test.py` now checks (as its first, blocking check) that `index.html` is byte-identical to what `scripts/build.py` would produce from current `src/` — if you edit `src/` and forget to rebuild, or hand-edit `index.html` and let it drift from `src/`, the smoke test fails with an explicit message telling you to rebuild.

## Commands

There is no test/lint toolchain beyond the smoke test (no npm scripts, no CI). Before every commit that touches `index.html` or `src/`:

```bash
python3 scripts/build.py                    # regenerate index.html from src/
python3 scripts/smoke_test.py index.html [--expect-version X.Y.Z] [--prev-version X.Y.Z]
```

The smoke test requires `node` on PATH (JS syntax check via `node --check`) and optionally `eslint@8` (`npm i eslint@8`) for a `no-undef` pass. It checks:
- `index.html` is in sync with `src/` (see above)
- version string bump in the header (`>vX.Y.Z<`)
- inline `<script>` blocks parse as valid JS
- no native `alert()`/`confirm()`/`prompt()` (must use `showAlertModal`/`showConfirmAsync` custom modals — `window.confirm()` doesn't work when the app runs in an iframe)
- no duplicate top-level `function` names
- no unescaped dynamic strings inside `onclick="...'${expr}'..."` (must go through `jsAttr()`/`esc()`)

Exit code 0 = pass, 1 = fail. Always run this before considering a change done.

## Deploy workflow

1. Copy current `index.html` into `backups/index_vX.Y.Z.html` (one backup per released version — see `backups/`).
2. Make the change in the relevant `src/js/*.js` file(s), bump the version string in `src/head.html`.
3. Run `python3 scripts/build.py` to regenerate `index.html`.
4. Run the smoke test above.
5. Commit/push both the changed `src/` file(s) and the regenerated `index.html` to `main` — GitHub Pages deploys automatically, no CI. Never commit an `index.html` that doesn't match a `python3 scripts/build.py` run against the `src/` in the same commit.
6. Add an entry to the top of the `## Changelog` section in `README.md` (Italian, terse, describes user-visible behavior and any required Supabase schema/Edge Function change). **`README.md` convention**: the program description (Funzionalità, Accesso, Stack tecnico, Backup, File nella repo, Note tecniche) comes first; the `## Changelog` section — newest entry first — comes after it, near the end of the file. Don't prepend changelog entries to the top of the file itself.

There's no local dev server needed — open `index.html` directly in a browser, or push and reload the Pages URL. Supabase URL/anon key are hardcoded in `index.html` (`SB_URL`/`SB_ANON_KEY`, around line 1305); this repo is private specifically because of that.

## Architecture

### Three "screens", one file
`switchScreen('dashboard'|'weekly'|'mappa')` toggles between three top-level views inside the same DOM/state. It hides all three first, then shows the requested one — don't reintroduce a two-branch if/else, it leaves combinations uncovered:
- **Dashboard** (`state.*`): commercial pipeline, operatori (staff registry with skills/certs), monthly staffing allocation (gg-uomo), Gantt, KPIs, map of active sites, Jira tools email mapping, admin log/reconciliation panels.
- **Pianificazione Settimanale** (`pw*` namespace, `#screen-weekly`): a weekly team-planning module with its own tab bar (`pwSwitchTab`): **Griglia** (team/site/tool assignment grid), **Ferie** (leave), **Mappa** (site map), **Controllo Produzione** (`cp*` — production tracking synced with Jira worklogs/production fields), **Doppia Week** (`dw*` — consecutive double-week away assignments).
- **Mappa** (`ml*` namespace, `#screen-mappa`, `src/js/mappa-live.js`): read-only overview of who is working where, opening on the current day. Own day/week navigation (`_mlAnno`/`_mlWeek`) deliberately **independent of `pwAnno`/`pwWeek`** — navigating here must never move the Griglia's working week. Combined filters (commessa/squadra/cantiere), weather on the pins, per-cantiere and per-commessa detail drawers. It adds **no new sync domain**: it reads `pwData`, `state.commesse_attive_meta`, `_geoCache`, the meteo caches and `controllo_produzione`. Because of that it re-renders for free on a Realtime pull (`mlOnDataChanged`, called at the end of `sbPull`); the 2-minute timer polls Jira only, and only while the screen is open and the browser tab visible. Scope is day (`0..5`), `ML_WEEK` (-1, whole week) or `ML_ALL` (-2, every week in `pwData`) — test scope with `< 0`, never `=== ML_WEEK`. `_mlTaskBySubtask`/`_mlTasks` are **cumulative caches, never reset**: subtask keys arrive piecemeal (visible week, then a commessa opened in the drawer), and clearing them made already-resolved cantieri fall back to "Stato n/d". They persist to `localStorage` (12h TTL), as do the historic production totals (6h); both are pure accelerators — the screen works identically without them. Items built from `pwData` are memoized on `_mlDataRev`, bumped by `mlInvalidateItems()` in `mlEnter`/`mlOnDataChanged`: if you add another path that mutates `pwData` while the Mappa is open, bump it there too or the view silently shows stale data.

- **Auto-pianifica** (`ap*`, tab of Pianificazione Settimanale): turns a list of cantieri + priorities into a *draft* Griglia for the shown week, applied to `pwData` only on explicit confirm (undo snapshot in `localStorage.ap_undo_v1`). Split in two files on purpose: `src/js/autoplan-solver.js` is a **pure module** (no DOM, no globals except `haversineKm`) — keep it that way, it is meant to be reused by an Edge Function (scheduled draft) and as tools for an LLM agent; `src/js/weekly-autoplan.js` holds UI, source adapters (paste/xlsx/manual/previous week — new sources = new adapter producing `apNormRiga` rows), context building and the write to Griglia. The solver assigns **single operators** (squadre are recomposed), never overwrites existing cells, and estimates effort from `controllo_produzione` (km ÷ median km/day per activity *family*, see `apFamigliaProduttiva`). The LLM must never write `pwData` directly: it can only call solver functions and propose a draft. External data reaches the solver only through `ctx` (`distanzaKm` from the OSRM cache, `meteo` penalties/blocks per riga+giorno, user `precedenze`) — fetch it in `weekly-autoplan.js`, never inside the solver. `apRisolvi` = greedy (`_apGreedy`) + local improvement (move an unsatisfied row earlier, keep it only if `valore` rises) + suggestions (moves that help a row but lower `valore`, left to the user); it is capped by `AP_MAX_RICALCOLI`/`AP_MAX_MS`, keep it deterministic (no randomness). **Trasferte**: most operators live far from the sites (often Perugia → Piemonte/Valle d'Aosta), leave home Monday and return Friday (except doppia week). So `maxKmTrasferta` caps only moves *between cantieri* during the week; the first trip from home (`partenza().casa`) has no cap, still costs its km, and beyond `kmViaggioMezzaGiornata` (200) that day yields half a productive day (`assegnazione.viaggio`/`produttivo`, 🚐 in the UI) while occupying the traveller's whole day. Simulated positions (`posSim`) count as starting points, so only the first day is a trip.
  - **Riparazione per imprevisti** (since v18.188.0, "⚡ Imprevisti" box in the same tab, `_ap.imprevisti` / `_ap.riparazione`): for a week *already* in Griglia. `apRiparaImpatto` (pure, in the solver) takes the week flattened to voci (`_apCelleSettimana`) + imprevisti (`assenza` operatore+giorni / `cantiere_fermo` cantiere+giorni) and returns the cells to remove plus solver rows: `sostituto` (1 op, same cantiere, same day, pinned via `dalGiorno`/`giorniEsclusi`) and `recupero` (lost days of a stopped cantiere, original team as `preferiti`). The context is built on a *virtual* copy of the week without those cells (`apBuildContesto({ data, assenti, sabato })`), so minimal change comes for free from the solver never overwriting cells. Apply removes cells (`_apTogliVoce`, keeps the other fields of the cell), optionally writes the absence into `pwFerie`, writes via the shared `_apScriviAssegnazioni`; the undo snapshot in `ap_undo_v1` carries `ferie` too. Past days are never touched.
  - **Assistente pianificazione** (`apc*`, `src/js/weekly-autoplan-chat.js`, since v18.186.0): a chat dedicated to the draft, separate from the generic `ai-assistant` widget. The Edge Function `ai-autoplan` (`supabase/functions/ai-autoplan/index.ts`) is a **one-step relay**: it owns the tool schemas and system prompt, calls the provider configured in `ai_assistant_settings` once and returns `{ text, toolCalls }`; the **tools run in the browser** (`APC_TOOLS`) on `_ap` and the client loops (max `APC_MAX_PASSI`). The transcript is provider-neutral (`user` / `assistant+toolCalls` / `tool+results`) and converted per provider server-side. Tools only touch rows/options/precedences and call `apCalcola({ silenzioso: true })` — never `pwData`; "Applica" stays a user click. Adding a tool = schema in the Edge Function **and** executor in `APC_TOOLS` (then redeploy). Provider config (`ai_assistant_settings`: provider, model, `provider_models`) is shared by `ai-assistant` and `ai-autoplan`; API keys are **one per provider** in Vault (`ai_assistant_get_provider_key(p_provider)` etc., service_role only). Providers: `gemini`, `groq`, `openrouter` (both OpenAI-format, via the shared `OPENAI_COMPAT` adapter) and `anthropic` — a new provider must be added to all three functions, the SQL `ai_assistant_key_name()` whitelist and the admin modal. Every modifying turn pushes an undo snapshot (`_apcSnapshot`) and a diff card; the draft keeps its `ctx` in memory for `apDiagnostica` (pure, in the solver).

- **Controllo anomalie** (`cpa*`, since v18.189.0, "🔍 Controllo anomalie" in Controllo Produzione; since v18.212.0 a **modal** `#cpa-modal`, z-index 99990, with one tab per check and anomalies grouped by day): same split as Auto-pianifica. `src/js/produzione-anomalie-core.js` is a **pure module** (`cpaRileva(input)` → anomalies with a proposed `correzione`, a `confronto` payload for the "In Griglia | Su Jira" view and an optional local `azione`) — keep it pure, it is meant to become LLM tools / a scheduled check. Four checks: `pianificato_senza_worklog`, `worklog_senza_pianificazione`, `epic_diverso`, `ore_squadra` (same commessa+squadra+day, day totals differing by ≥ `diffOreSquadra`, per-browser setting in `localStorage.cpa_pref_v1`; zero-hour operators and operators on several squadre that day are left out), `mysond_diverso` (since v18.217.0: day total on Jira vs MySond, only where MySond is loaded; travel — `att1`/`att2` matching "Viaggio" — and "ORE NON LAVORATE" normally don't go on Jira, so Jira is fine anywhere between MySond work hours without and with travel, ± `diffOreMysond`; `cpaMysondRipartisci`/`cpaMysondScarto` are shared with the MySond column's amber colour; MySond data comes from `_cpMysond`, valid only when `_cpMysondDi` equals the shown week, never stored in `_cpa.base`), `ore_scoperte_maltempo` (since v18.219.0: planned days with partial Jira hours, ≤ `oreGiornata` − 1, not already covered by another low-hours check, listed only when bad weather is *probable*). Weather evidence (`cpaMeteoEvidenza`, pure) reads the observed weather through `input.meteoDi(cantiere, giorno)` (built in the adapter from `pwMeteoInfoFor`/`pcInfoFor`/`pwMeteoSeverityFor`, past days only) and counts rainy hours in the 8–17 window (`CPA_METEO_FASCIA`; Open-Meteo hourly values are "previous hour", so slot start = hour − 1); `_cpaAnnotaMeteo` adds `a.meteo` to `pianificato_senza_worklog`, `ore_squadra` (low members, `m.meteo`) and `mysond_diverso` when Jira is below. `_cpaMeteoCarica` loads the week's history (`msLoadRange` + queued `msEnsurePast`) once per week per session when the modal renders, and on Ricontrolla. The km checks (duplicates / out of scale) and `worklog_parziale` were removed in v18.212.0. `src/js/produzione-anomalie.js` gathers the input: Griglia+Ferie cells, worklogs **re-read** from `jira-sync-worklogs` (read-only, for every operator in the week's Griglia — the saved "Ore Jira" only covers planned cells), Epics of the Griglia subtasks via `mlEnsureTaskStatus` (same cumulative caches as the Mappa; subtask is the only cantiere→Epic link, no name matching), and an index of the subtasks of **all** of `pwData` (`_cpaIndiceSottotask`) to say which cantiere a worklog ticket belongs to. Jira is read on "Avvia/Ricontrolla" (`_cpa.base`) or, for one anomaly, by its "↻ Ricontrolla" (`cpaRicontrollaVoce`: re-reads worklogs + subtask Epics of the operators involved only and merges them into `_cpa.base`); after a fix, a threshold change, reopening the modal or a Controllo Produzione re-render `_cpaRicalcola()` re-runs the engine locally on the current Griglia/Ferie. It **never writes Jira**: the only action is adding the proposed (user-editable) Griglia cell for a worklog without planning — proposal from the ticket's subtask, else same-Epic cantiere of the week, else the cell marked absent that day, else the nearest planned day — removing that day's absence from `pwFerie` when needed. Each week keeps its own check (since v18.214.0): `_cpaCache['anno|week'] = { base, risolte, proposte, propMod }`, swapped in by `_cpaAllinea()` when `pwAnno`/`pwWeek` change (never reset), and the Jira reads (`base`, without the single worklogs' comments) persisted in `localStorage.cpa_cache_v1` for the last `CPA_CACHE_MAX` weeks; Jira is re-read only on explicit Ricontrolla (auto-read only the first time a week is opened). `cpaAvvia`/`cpaRicontrollaVoce` store their result for the week they started on (`_cpaMemorizza`), even if the user changed week meanwhile. Dismissed items live in `localStorage.cpa_ignorate_v1`.
  - **Export PDF** (since v18.218.0, `src/js/produzione-anomalie-pdf.js`, "📄 Esporta PDF" in the modal bar): open anomalies of the shown tab (`_cpa.filtro`, '' = one section per check), ignored/fixed ones excluded. jsPDF + autoTable (same as the Controllo Produzione report). Writes nothing, except through the worklog editor below.
  - **Correzione worklog** (`cpTlWl*`, `src/js/produzione-timeline-worklog.js`, since v18.230.0, modal `#cptl-wl-modal` z-index 99995): admin/responsabile fix worklogs left wrong by bad subtask transitions. Before/after goes to `activity_log` server-side. **Author** (since v18.237.0): Jira's REST API can't set a worklog's author (it's always the caller = service account), so with a Tempo token (env secret `TEMPO_API_TOKEN`, else Vault `tempo_api_token` via `tempo_get_api_token()`, service_role only) the function writes through Tempo (`authorAccountId`): creates are authored by the subtask's **assignee** (else the operator), and an update of a worklog authored by the service account (`/myself`) re-authors it to the assignee (Tempo may recreate the Jira worklog with a new id — re-read via `tempo-to-jira`); other updates and deletes stay plain Jira calls. Hideable via «🧩 Funzioni» (`controllo:timeline-modifica`, `cpTlWlPuo()` also turns bars back into Jira links).

- **Indietro / Avanti** (since v18.216.0): session-only undo/redo, one history per screen. Engine `undoCreaCronologia(opts)` in `src/js/undo-history.js` (also the shared Ctrl+Z/Ctrl+Y listener — ignored inside text fields and when a full-screen modal is open — and `undoToast`). It does **not** instrument individual actions: each module calls `registra()` from its single save chokepoint; after a 250ms debounce (one action saving several domains = one step) the engine diffs `snapshot()` — a Map of fine-grained keys → JSON — against the last known one and pushes only the changed keys with before/after JSON. Whoever replaces the data from outside calls `flush()` **before** (pending local change becomes a step) and `rebase()` **after** (no step), so a colleague's changes are never undone; applying a step whose keys changed since asks for confirmation. flush/rebase go through a promise queue (snapshots may be async).
  - **Pianificazione** (`pwUndo*`, `src/js/weekly-undo.js`, buttons `#pw-undo-btn`/`#pw-redo-btn` in the Griglia toolbar): `pwData`, `pwFerie`, `pwFerieDettagli`, `pwDoppiaWeek` flattened two levels deep (`[anno][week]`, or `[noteGenerali][anno]`…); empty weeks (`[]`/`{}`, created just by viewing) count as absent. Hooks: `pwSave`/`pwFerieSave`/`pwDwSave` → `pwUndoRegistra()`; `pwLoad` and `sbPull` → `pwUndoFlush()`/`pwUndoRebase()`. A step on another week moves `pwAnno`/`pwWeek` there.
  - **Dashboard** (`dbUndo*`, `src/js/dashboard-undo.js`, `#db-undo-bar` in the header, shown only on the Dashboard by `switchScreen`): the core keys saved by `saveState()` plus `commesse_attive_extra` (written to storage *before* `saveState`, so read with `sget`). Arrays with unique `id` (operatori, pipeline) are tracked per element + id order, objects per property, the rest (staffing has no id) whole; `alloc_mensile`/`saturazione` are left out (derived). Hooks: `saveState` → `dbUndoRegistra()`; `sbPull` → `dbUndoFlush()` before applying; `loadState` ends with `dbUndoRebase()`. Applying writes state/storage, then `saveState('Indietro (annulla)'|'Avanti (ripristina)')` + `loadState()` so derived data (commesse_attive, allocations) is recomputed as on load.
  - **A new writer of these structures must go through the save chokepoints** (`pwSave`/`pwFerieSave`/`pwDwSave`/`saveState`; doppia week now saves only via `pwDwSave`), or its change is silently folded into the next step. A new core key = add it to `saveState`/`loadState` and to `DB_UNDO_CHIAVI`.
- **Funzioni nascoste** (`sbFn*`, `src/js/sb-funzioni.js`, since v18.209.0, admin "🧩 Funzioni" button in the header): admin hides pages/buttons from non-admins. Shared state in Supabase `app_funzioni_nascoste` (row present = hidden; select all, insert/delete admin only; own Realtime channel). Pages reuse the `sbCanSeePage()` keys (so navigation/redirects come for free); buttons/sections are hidden by a generated stylesheet (`#sb-fn-style`, `display:none !important`) built from the `sel` of each entry in `SB_FN_FUNZIONI`, so it also covers elements re-created by renders. A new hideable feature = one entry in `SB_FN_FUNZIONI` with a stable selector (give the element an id/class). UI-only, not a permission.

Function names are prefixed by module: `pw*` (weekly planning), `cp*` (production control), `dw*` (double week), `jst*` (Jira structure per comune), `pwUndo*`/`dbUndo*`/`undo*` (Indietro/Avanti), `ml*` (Mappa screen), `ap*` (Auto-pianifica), `cpa*` (Controllo anomalie), `sb*` (Supabase/sync/auth), plus generic dashboard render functions (`renderOperatori`, `renderCommesse`, `renderGantt`, etc.).

### State & persistence — four independent sync domains
State is split into four domains, each its own row in Supabase table `staffing_state` (`payload` jsonb), each with independent dirty-tracking, remote timestamp, and conflict detection — NOT one big blob:

| Domain | Row id | Dashboard state | Push debounce |
|---|---|---|---|
| core | `SB_ROW_CORE` (1) | `state.*` (pipeline, operatori, staffing, commesse) via `saveState()`/`loadState()` | 3s (`sbScheduleAutoPush`) |
| planning | `SB_ROW_PLANNING` (2) | `pwData` via `pwSave()`/`pwLoad()` | 500ms (`_sbPwPushTimer`) |
| ferie | `SB_ROW_FERIE` (3) | `pwFerie` | 500ms |
| dw | `SB_ROW_DW` (4) | double-week assignments | 500ms |

`_sbDirty{core,planning,ferie,dw}` and `_sbRemoteTs{1..4}` track push state and detect remote-vs-local conflicts per domain independently. Supabase Realtime subscribes to `staffing_state` and auto-pulls when another user saves. Reads/writes go through `sget`/`sset` (wrap `window.storage` if present, else `sessionStorage`), not directly against Supabase, except in `sbPush`/the domain load functions.

Some local-only UI state (last active tab, last viewed week/year, scroll position per tab, tools cache) lives in `localStorage`, separate from the synced domains above — it's per-browser convenience state, not shared data.

### Jira integration (Edge Functions, read side does not write back except for production KM)
Supabase Edge Functions bridge to Jira. **Since v18.173.0 their source is versioned in this repo under `supabase/functions/<slug>/index.ts`** — but only for functions touched since then; the older ones still live only on Supabase (read them with the Supabase MCP `get_edge_function`, and drop the source into `supabase/functions/` when you next change one). There is no CI: deploying is a separate step (Supabase MCP `deploy_edge_function` or the Supabase CLI), so a commit here does **not** update the running function.
- `jira-list-strumenti` — lists "Strumentazione" issues (project GAR) for the tools dropdown in Griglia; cached in `localStorage` (`pw_strumenti_cache`). Read-only.
- `jira-sync-worklogs` (`supabase/functions/jira-sync-worklogs/index.ts`) — pulls real worklog hours + ticket/epic links into Controllo Produzione's "Ore Jira" column. Since v18.210.0 each ticket also carries `summary` and `worklogs: [{started, seconds, comment}]`, saved as-is in `controllo_produzione.jira_tickets` and drawn by the hover infographic on "Ore Jira" (`cpOreJira*`, `src/js/produzione-orari-jira.js`, times converted to Europe/Rome).
- `jira-update-production` — writes/reads the "Actual Production" custom field on subtasks. Uses a **delta model**: each cell tracks the last value it wrote (`km_jira_last`); sync applies only `km_cad - km_jira_last` (can be negative) so the app's contribution is replaced rather than re-summed, and values written by other sources are preserved. Operates **per ticket**, since one operator can have production on multiple tickets/comuni the same day.
  - **Campo per commessa** (since v18.224.0): commesse with the new format (for now SINFI) write to "KPI_Quantità lavorata" instead of "Actual Production" — subtask only, no parent-Task delta, no progress %. The choice is an app setting (`cp_campo_produzione`, selector on the commessa row of Controllo Produzione, admin/responsabile) passed as `campo` in `updates`/`reads`; it **cannot be detected on Jira** (verified 26/10/2026: KPI_Quantità lavorata is on the edit screen of every subtask, and SINFI shares project AI029 with other commesse) — don't reintroduce screen/editmeta detection. The delta history is per field: `km_meta_by_ticket[key].campoLast` (absent = Actual Production); if it differs from the commessa's field, the next send writes the full value on the new field and leaves the old one alone.
  - **Verified vs read** (since v18.224.0): `km_meta_by_ticket[key].fonte` = `report` | `manuale` (confirmed by the user) | `jira` (adopted from Jira during sync — usually the operator's placeholder "1"). Only `report`/`manuale` are sent and count as "✓ allineato"; `jira` shows "👁 Verifica". Rows saved before the column infer it in `cpRowToCell` (Ore Report filled = report, else jira). Any new writer of `km_by_ticket` must set `fonte` via `cpKmMetaSet`, or its values look unverified.
- `jira-list-epics`, `jira-list-tasks`, `jira-create-subtask` — used by Griglia's "🎫 Sottotask Jira" feature to create subtasks for planned sites. Epic and Task are picked **by hand** in that modal (once per cantiere+attività) and the choice is **not persisted**: only the resulting subtask key is stored.
  - **Daily subtasks** (since v18.229.0): one subtask per operatore + cantiere + attività + **giorno**, summary `Attività - Comune - Cognome - Gio 29/10/2026`, start date = due date = that day (per item, only if the project has the fields), original estimate `1d`. Planners create them Thursday/Friday for the next week and again during the week for changed days; days that already have one are skipped. The link lives in the Supabase table `pw_jira_subtask` (one row per voce+giorno, unique on anno/week/commessa/cantiere/operatore/attivita/giorno; select all, write admin/responsabile; own Realtime channel), **not in `pwData`** — at ~200 subtasks/week it would have bloated the planning row that is pushed on every save. `src/js/weekly-jira-subtask-db.js` (`pwJsub*`) loads all rows at login (`pwJsubLoad`, before `sbPull`, paginated) into an in-memory index `anno|week|commessa → mapKey → entry`, so every reader stays synchronous. Daily map key: `comune|||operatore|||attività|||giorno`. Weekly entries saved before stay in `bc.jiraSubtask[comune|||operatore|||attività]` (or `comune|||operatore` before v18.182.0): never written any more, still read, and they cover every day of their week. Indietro/Avanti does not touch the table (like Jira).
  - **Catalogo attività / KPI_Quantità target** (`ca*`, `src/js/commessa-attivita.js`, since v18.229.0): `state.commesse_attive_meta[commessa].attivita = [{ nome, produttiva, kpi_target, unita, activity_type: {id, label}, alias: [] }]`, edited from the commessa modal («🏷️ Attività e KPI», draft saved by the modal's «Salva»). With a catalog, the Griglia attività input gets a `<datalist>` (catalog + `CA_ATTIVITA_SERVIZIO`, never productive) and `pwUpdateAttivitaCantiere` rejects names not in it and stores the catalog name for an alias; commesse without a catalog stay free text, and old `pwData` names are **never rewritten** — always resolve a Griglia name with `caTrova(commessa, testo)` (name, alias, service entry; tolerant to case/accents/spaces). `kpi_target` is the **daily target per squadra**: `caKpiTargetVoce` divides it by the operators of the same Griglia squadra on the same cantiere + same catalog entry that day (alone = full target). In subtask creation it becomes per-item `kpiTarget`; the Edge Function finds the field by name («KPI_Quantità target», same tolerant match as «KPI_Quantità lavorata») on the subtask create screen (`mode: 'fields'` returns it as `extraKey: 'kpiTarget'`) and fails the item if the project lacks it. On commesse with a catalog Target Production is not sent any more; Activity Type is proposed from the catalog first (`pwJiraActivityTypeGuess`).
  - Always go through `pwJiraSubtaskLookup`/`pwJiraSubtaskEntry(bc, comune, operatore, attivita, giorno[, anno, week])` — daily entry first, then the weekly one (legacy no-attività fallback only when the operator has a single attività on that comune) — or `pwJiraSubtaskMappa(bc, anno, week)` (all entries of a block, both sources, each with `cantiere/operatore/attivita/giorno`; `giorno` null = weekly) + `pwJiraSubtaskEntriesFor`; never index `bc.jiraSubtask` or the table index directly. Pass the attività through `pwJiraAttivitaSottotask` (a day without attività belongs to the operator's other attività on that cantiere). Writes: `pwJiraSubtaskMarkBadges` (batch upsert), `pwJiraSubtaskBadgeRemove`, `pwJsubCambiaOperatore`, `pwJsubElimina`.
  - The Edge Function dedups a daily item (`data`) by reading the operator's subtasks under the Task once per Task+assignee and matching the `gg/mm/aaaa` marker or due = start = day (a summary with `Week N` never matches); items without `data` keep the old `Week N` rule. The client sends items in chunks of `PW_JIRA_CHUNK` (20) and recalculates Production Weight at the end with one `mode: 'recalcWeights'` call per Task (parallel PUTs), because daily subtasks made single calls exceed the function time limit.
- `jira-worklog-edit` (`supabase/functions/jira-worklog-edit/index.ts`, since v18.230.0) — **writes** worklogs: create/update/delete one worklog with the Jira service account (needs «Edit/Delete All Worklogs» on the project), admin/responsabile only (role checked server-side), logs before/after in `activity_log`. Used only by the Timeline worklog editor (see above).
- `jira-struttura-comune` (`supabase/functions/jira-struttura-comune/index.ts`, client `jst*` in `src/js/jira-struttura-comune.js`, since v18.231.0) — creates the per-comune hierarchy (e.g. Iniziativa → Epic → Task, **never subtasks**) by copying the commessa's **MODELLO**, a real tree in Jira whose root key is in `state.commesse_attive_meta[commessa].jira_modello` (`{ key, project, base, nodi: [{key, summary, tipo, livello, parentKey}], letto_il }`, edited from the commessa modal «🧩 Modello», saved by the modal's «Salva»; must be in the commessa's `jira_project_code` project — AI029 is shared by several commesse, so the template is explicit per commessa, never found by name). No template = the «🏗️ Crea strutture comuni» service is disabled. Summaries: `_?MODELLO` → comune name. Fields: template values for fields on the create screen of that issue type (createmeta), except dates, estimates, sprint/rank/epic-link and strings citing a template key (automation-filled parent links); a field Jira rejects is dropped and reported. Dates (since v18.233.0): where the template has `duedate` / Start date pianificato (`customfield_13093`) filled — in SINFI the Tasks, which a Jira create validator rejects without them plus Target Production — the dates chosen in the creation modal (`date: { inizio, scadenza }`) are written instead. Idempotent: an existing root (same type, same summary, same parent) is completed, children matched by type+summary under the same parent — manual structures get "adopted". Summaries compare via `chiaveTitolo` (pieces split on "-", any order): pre-template comuni name Tasks "Rilievo Auto - Cividate Camuno", not "Cividate Camuno - Rilievo Auto"; plain summary matching would duplicate them. Modes `modello` (read tree + copy plan) and `comune` (`dryRun` preview mandatory in the UI, one call per comune). Since v18.234.0 every «da creare» node in the preview has a checkbox: checking a node checks its missing ancestors, unchecking it unchecks its descendants; unchecked template keys go as `escludi` and come back as `saltato` («non selezionata»). The function imports supabase-js from `npm:` (the `jsr:` fetch timed out in the Supabase bundler). Without dryRun the keys go to the Supabase table `jira_struttura_comune` (unique commessa+`comune_norm`; select all, written only by the function with service_role) + `activity_log`; admin/responsabile only (role checked server-side). Since v18.235.0 the same creation modal also opens from the Griglia: «🏗️ Strutture comuni» in the commessa block header (`pwJstApri`, `data-help-key="pw-strutture-jira"`), rendered only when `jstModelloDi(meta)` is set, using the *saved* template. The Griglia subtask modal only hides the template's Epics (`jstChiaviModello`): Epic/Task are still picked by hand. A v18.231.0 auto-proposal from the table (template Task ↔ Griglia attività mapping) was removed in v18.232.0 at the user's request — for now the service only creates the structure.
- `jira-task-status` (`supabase/functions/jira-task-status/index.ts`) — read-only; takes subtask keys, walks the `parent` field up to the Task, returns the Task's status. Used by the Mappa screen. With `statoDa: true` (Controllo Produzione's Stato poll, since v18.220.0) it also returns, for subtasks in category `indeterminate`, `statoDa`/`statoDaAutore` = last transition into the current status, from the changelog (`statuscategorychangedate` is not enough: IN PENDING → IN PROGRESS stays in the same category). Subtask workflow: TO DO → IN PROGRESS ⇄ IN PENDING → DONE, and a **Jira automation creates the worklog only when the subtask leaves IN PROGRESS**, so the open IN PROGRESS segment is the only trace of ongoing work: `cpLavoroInCorso` turns it into the "▶ +h in corso" quota under Ore Jira (today's rows only) and the hatched segment in the hours infographic. Display only, never saved. Because of the "not persisted" point above, **the subtask is the only certain cantiere→Task link** (the `jira_struttura_comune` table is not used to infer status): do not add name/summary matching between a cantiere and a Task — it was considered and deliberately rejected (risk of wrong or ambiguous matches). Cantieri without a subtask are shown with no status, on purpose.

When touching this area, read the version history in `README.md` (v18.28–v18.32) — the KM/production-sync design went through several iterations and the delta/per-ticket model replaced an earlier single-cell model; don't regress to summing absolute values.

### Geocoding & Mapping
Two public, free services power location-based features (no API key needed):
- **Tile stradali**: every Leaflet map gets its base layer from the single helper `mapStreetLayer()` (in `src/js/weekly-nav.js`). It uses **CARTO Voyager**, not `{s}.tile.openstreetmap.org` — OSM deprecated the `a/b/c` subdomains and now serves "Access blocked — App is not following the tile usage policy" tiles instead of the map (fix v18.174.0). Don't reintroduce a direct OSM tile URL; change the provider in that one function. `mapAddSatelliteToggle()` defaults every map to **satellite** (Esri) and remembers the user's pick in `localStorage.map_base_layer`, because the street layer has been unreliable in this environment.
- **Geocoding sentinel**: `_geoCacheSaveSingle(key, null)` persists a *sentinel row* (`lat 0`, `lng 0`, `label '[non trovato]'`) to the Supabase `geo_cache` table. In memory a not-found lookup is `null`, but after a reload `_geoCacheLoad()` reads that row back as a **valid-looking coordinate at (0,0)**. Read coordinates through a filter that rejects it (`mlGeo()` in `mappa-live.js`), never `_geoCache[key]` directly, or non-geocodable sites get drawn off the coast of Africa and silently drop out of "not located" counts. The weekly Mappa squadre still reads it directly — a known pre-existing issue, not yet fixed there.
- **Nominatim** (OpenStreetMap Geocoding, `https://nominatim.openstreetmap.org`) — converts site/city names → lat/lng coordinates. Results cached in `_geoCache` (key: lowercase trimmed name) and persisted in `localStorage` (`geo_cache_v1`) to avoid re-querying. Used by Mappa Squadre (weekly map), Pianifica Spostamenti (route planner), and upcoming "Ricerca Dipendente-Cantiere" feature. When a geocoded location does not match expectation, users can manually correct it in Mappa Squadre (pencil icon ✏️ on each listed site) — corrections are applied to the shared cache, affecting all weeks where that site name appears.
- **OSRM** (Open Source Routing Machine, `https://router.project-osrm.org`) — real-world driving distances/times (road network) and route geometries. Used only by Pianifica Spostamenti (`/table` for distance matrix, `/route` for polyline to draw on map). Queries are not cached; results are stored locally in `localStorage` (`pw_spost_v1`, per-browser state).
- **Open-Meteo** (Weather API, `https://open-meteo.com`) — fetches daily and hourly weather for planned sites. Called on-demand when rendering a Griglia day, with 1-hour TTL cache (in-memory, not persistent). Forecast only covers today onward.
- **Storico meteo** (`src/js/meteo-storico.js`, `ms*`, since v18.181.0) — for **past** days, `pwMeteoInfoFor`/`pcInfoFor` read only the observed history (`_meteoStorico`/`_pcStorico`), never the stale forecast still in cache. History lives in Supabase tables `meteo_storico` (key `pos_key` "lat,lon" 2 decimals + `data`, from `archive-api.open-meteo.com`) and `pc_storico` (key `data` + normalized cantiere, the bulletin of that day already matched to the cantiere; `info` null = comune not in the bulletin). Filled client-side: visible week/day first, then a background backfill of all of `pwData` from the first planned day (`msStartBackfill`, capped at 60 PC bulletins per session, ~1MB each). Rows younger than 7 days are `definitivo = false` and get re-fetched. All fetches go through the `msRun` queue; writes are idempotent upserts. Use `meteoGeoFor()` (rejects the geo sentinel) rather than `_geoCache[key]` in meteo code. Past-day entries have `precip` (mm) instead of `pop` (%): format with `pwMeteoRainLabel()`.

### Data types & structures
Key data structures to know when working with different modules:

- **`pwData[anno][week]`** — Weekly planning grid (Griglia). Structure: array of commessa blocks, each `{ commessa, commessaId, squadre: [{ nome, operatori: [{ nome, giorni: {0..5: {cantieri: string[], attivitaCantieri?: string[], attivita: string}} }] }] }`. Since v18.182.0 each cantiere has its own attività (`attivitaCantieri`, aligned by index with `cantieri`; the same cantiere may appear twice with two attività); `attivita` is kept as the cell summary (distinct values joined by ", ") for per-cell readers and must only be written via `pwCellSyncAttivita()`. Read pairs with `pwCellVoci(g)`; cells without `attivitaCantieri` (pre-v18.182.0) apply `attivita` to every cantiere. Synced to Supabase `staffing_state` row `SB_ROW_PLANNING` (row id 2), domain key `pw_data`.

- **`state.operatori[]`** — Operator pool (Dashboard → Pool operatori). Structure: `{ id, nome_esteso, email, skills: string[], attestati: [...], provincia, regione, contratto_tipo, contratto_inizio, contratto_fine, ... }`. Skills and provincial origin are used for matching when assigning to sites.

- **`state.pipeline[]` / `state.commesse_attive[]` / `state.commesse_attive_meta{}`** — Project pipeline and active commesses (projects). Structure: `{ id, progetto, cliente, skills: [], attestati_richiesti: [], regione, provincia, codice_progetto_jira, ... }`. Region/province are used for geographic distance calculation ("📍 operatori più vicini").

- **`pwFerie[anno][week]`** — Weekly absences (leave, unavailability). Structure: array of arrays, `[operatore_idx][giorno]` = `'ferie'` | `'non_disponibile'` | undefined. Synced to Supabase `staffing_state` row `SB_ROW_FERIE` (row id 3), domain key `pw_ferie`.

- **`_geoCache`** — Persistent geocoding results. Structure: `{ 'lowercase name': { lat, lng, label } | null }`. Null entries mark sites that were searched but not found by Nominatim; they are still cached to avoid re-querying. Persisted in `localStorage` as `geo_cache_v1`.

### Auth & roles
Supabase Auth (email+password). Role is read from `auth.jwt() -> 'user_metadata' ->> 'role'` / `_sbUser.user_metadata.role`; `sbIsAdmin()` checks for `'admin'`. Admin-only: activity log (`activity_log` table, via `sbLogActivity`), active-sessions panel (`active_sessions` table, heartbeat every 45s, stale sessions >5min pruned), name-reconciliation debug section. Assigning admin is a manual SQL statement against `auth.users` (documented in `README.md`).

### Hard-won conventions (violating these has caused real regressions — see changelog v18.13–v18.18, v18.41)
- **Never use native `alert()`/`confirm()`/`prompt()`** — use `showAlertModal(msg)` / `await showConfirmAsync(msg, label)`. Native `confirm()` silently fails inside an iframe.
- **Escape all dynamic strings in `onclick="..."` attributes** with `jsAttr()` (for the attribute string) or `esc()` (for HTML content) — names with apostrophes (e.g. "D'Ivrea") break unescaped inline handlers. This is enforced by the smoke test.
- **Avoid nested template literals** — they've caused JS parse errors in this codebase; prefer string concatenation + `data-*` attributes for building HTML with dynamic attributes.
- **No duplicate top-level function names** — also enforced by the smoke test; this file is edited by hand/by search-replace often enough that duplicates have slipped in before.
- `INITIAL_DATA` is a minimal/empty fallback, not real data (real data lives only in Supabase since v18.17) — don't reintroduce a large hardcoded seed blob.
- **Every button in Pianificazione Settimanale has a right-click guide** (since v18.225.0). The resolver (`helpKeysFor` in `src/js/dashboard-crud-helpers.js`) walks up from the clicked element and takes the first key with a text in `HELP_TEXTS`: `data-help-key`, then `'#' + id`, then each call in the inline `onclick`/`onchange` (`'fn:arg'` when the first argument is a string literal, then `'fn'`; `closeModal`/`if` skipped). Texts live in `src/js/weekly-guida.js` (Italian, for planners: what it does, what it writes — shared Griglia, Jira read/write, this browser only — and what can't be undone). A new button = a text there; add `data-help-key` when the button has no id/inline handler or shares its function with buttons that mean something else (e.g. `apSetCampo(this)`). Never give a text to `closeModal`/`cpaToggle` (close buttons use them). Text fields and `a[href]` keep the browser menu; a cell's own `oncontextmenu` must start with `if (helpGuidaSuBottone(ev)) return true;` so the buttons inside it still show their guide.
- **Confirm/alert modals must always render on top of every other modal.** `showConfirmAsync`/`showAlertModal` render into `#modal-root` with class `.modal-backdrop` (z-index kept as the highest of any fixed-position modal/overlay in the app — currently 100050). Any new modal (`position:fixed` + its own `z-index`, e.g. a new `sb-*-modal` panel) must stay below it, otherwise a confirm/alert triggered from inside that modal renders invisibly behind it (happened with "Elimina utente" behind "Gestione utenti", fix v18.137.0). Enforced by the smoke test (check 8) — bumping any modal's z-index to/above `.modal-backdrop`'s fails the build; raise `.modal-backdrop`'s z-index instead if a new modal genuinely needs to sit higher than the current ceiling.
